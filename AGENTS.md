# coding-agent-kanban-turns

The `coding-agent-kanban-turns` Claude Code plugin, in TypeScript: a pane that lists the kanban turn responses' Decide items as they're raised, and the same buttons under each reply in the transcript, that answer them. See `README.md`. Plans live in `agents/plans/`; `agents/plans/README.md` is their overview.

## Layout

- `plugin/`: the plugin, the marketplace's source (`.claude-plugin/marketplace.json`).
  - `hooks/`: the effects: `register.tsx` registers every hook, and `settings.ts` reads the settings files.
  - `cli/`: the kanban CLI, which runs the core outside the engine, for the derived skill and harnesses with no plugin hooks: `run.ts`, its commands (`count`, `rollup`, `due`, `lint` and `turn-id`), each a thin edge over the core function the plugin's tools and hooks call, `due` saying whether the full roll-up is due by the roll-up interval, `lint` giving `kanban_lint`'s text for a draft and the turn's end's for the last final response, the one the turn's end lints, and its arguments; `neutral.ts`, the neutral turns it reads from stdin as JSON, strictly, beside the Claude Code adapter it reads a `--transcript`, or by default the session's own transcript `CLAUDE_CODE_SESSION_ID` names, through; and `kanban.ts`, its one file with effects, which finds that transcript and reads the clock. The flake bundles it into `kanban.js`, for Node 20 or later. The plugin's build carries `kanban.js` in the derived skill's `scripts/`, with `kanban`, a wrapper that runs it with the Nix store's `node`.
  - `src/`: the pure core, no `claude-code` import and no I/O, so Node type-checks and tests it, in a folder per concern:
    - `protocol/`: `spec.ts`, generated from the spec, and `fragments.ts`, from the prose fragments; `rules.ts`, which derives the patterns and labels several core files share from the spec; `kinds.ts`, the option kinds' glyphs and letters, and which kinds the instructions teach; `prose.ts`, which fills the fragments' placeholders from the spec and assembles them; `instructions.ts`, what the plugin tells the agent: the whole turn-response format and its tools; and `tools.ts`, the `kanban_outstanding` and `kanban_lint` tools' names, descriptions and schemas.
    - `transcript/`: the turns and what they hold. What settles items, the count line and the roll-up read harness-neutral turns (`Turn` in `types/index.d.ts`), which the Claude Code adapter, `claude-code.ts`, builds from the session's JSONL records, reports' names, Decide items and whether a turn has a final response included; `turns.ts` reads a turn's texts, `reply.ts` a reply's text, once, into the blocks every reader of a reply reads but the lint (headers, items with the lines under them, the 📌 roll-up's start, topic headers, code blocks and the rest), and `reports.ts` a report's names and a summary's branch-shaped code spans. `instructed.ts` is the one other module that reads those records, for whether the agent's instructions reached the conversation, from the hooks or a load of the plugin's skill.
    - `items/`: the Decide items, the draft's answers, the items raised in the session, what the turns leave open, and what each item frees, read from its `Frees:` line; `roll-up.ts`, what `kanban_outstanding` gives; `roll-up-due.ts`, when the full roll-up is due, from the turns' times.
    - `lint/`: the reply lint, `reply.ts`, which `kanban_lint` and the `turn.complete` hook run.
    - `pane/`: what the pane and a reply's buttons draw: the text, the branches and turn groups with their folds, the layout and the links.
    - `config/`: the settings, read and merged.
    - `text/`: what the pane, the prose and the patterns share about text: `cells.ts`, the cells a string takes in a terminal, `words.ts`, a list of words in a sentence, and `patterns.ts`, text escaped to match literally in a regular expression.
    - `json/`: `fields.ts`, what the core reads JSON input it never typed with: whether a value is an object, a field of it, and JSON text parsed without a throw.
  - `spec/`: the protocol's checkable rules, the same for every user: `kanban.yaml` (the lists, each with the way its items are settled, which `SETTLERS` in `src/items/outstanding.ts` holds a settler for, the option kinds, each marked whether the instructions teach it or only read it, the commands, the reference grammar, the `Frees:` line, an item's subject key, which matches it across rewordings of its summary, with the branch shape a report names a Waiting item by, the roll-up, the 🔖 tag and the rule characters), its JSON Schema `kanban.schema.yaml`, and `kanban.json`, a generated copy for readers that aren't TypeScript; and `fragments/`, the prose rules a parser can't check, a Markdown file per topic, naming each list, glyph or command by a placeholder, `{{lists.decide.header}}`, that the spec fills. The core reads the rules only from `src/protocol/spec.ts` and the prose only from `src/protocol/fragments.ts`, never the files at run time.
    - `cases/`: the golden cases, one YAML file each, beside their JSON Schema `case.schema.yaml`: a transcript of neutral turns and what the core gives for it, its open items, outstanding items, count line, what each item frees, each turn's command and each reply's lint findings. A case marked `example: false` breaks a rule on purpose, so it is no worked example.
  - `tools/`: the build step that compiles the spec and the fragments (`spec/load.ts`, pure, and `spec/compile.ts`, which reads and writes the files), refusing a fragment whose placeholder the spec has no value for, and `plugin-test.sh`.
    - `spec/strict.ts`: reads a data file and its schema strictly, for both the spec's build step and the golden cases.
    - `spec/cases.ts`: reads a golden case and works out what the core gives for it.
    - `skill/render.ts`: the derived skill's text, pure: `SKILL.md`, its frontmatter and the fragments `SKILL_FRAGMENTS` names, filled in from the spec with the CLI's script in place of the plugin's tools, then the CLI's usage and the worked examples' list; and a worked example per golden case not marked `example: false`, refusing one that draws an option kind the instructions don't teach. `skill/build.ts` writes them into a folder, for the flake.
  - `skills/`: the derived skill, `coding-agent-kanban-turn-responses/`, named by the spec's `skill.name`, as the flake builds it for a git install: `SKILL.md`, `examples/`, `scripts/kanban.js` and the YAML parser's licence. Committed for the marketplace's git install, which has `kanban.js` alone, for Node 20 or later; `nix flake check` holds the whole folder to the flake's build file for file and mode for mode, and `refresh-skill` lays the flake's for a commit. Never edited by hand.
  - `defaults/config.yaml`: every setting with its default and a comment; a user's own `config.yaml` merges over it.
  - `types/index.d.ts`: the shapes and the `$.state` contract, self-contained as `claude plugin validate` asks.
  - `vendor/`: the runtime libraries the core imports by a relative path, a folder each, `yaml/` alone. The engine loads only the plugin's own files, so the flake bundles each into one ES module in its folder (`nix/scripts/vendor/bundle.sh`), with its `LICENSE` beside it. The bundles are committed, for the marketplace install, beside their self-contained types; `nix flake check` holds them to the flake's byte for byte, and `refresh-vendor` lays the flake's after a change to the libraries, the bundling or the flake's inputs (`update-flake`), for a commit.
  - `test/`: the tests.
    - `unit/`: the core's tests, `node --test` with Jest's standalone `expect`, and `fast-check` for the property tests, in folders mirroring `src/`; `protocol/golden-cases.test.ts` runs every golden case, so a new case needs no new test code.
    - `engine/`: the pane, the count line above the prompt, a reply's buttons and the tool row driven through the engine, `claude plugin test`; `tools.test.tsx`, the `kanban_outstanding` and `kanban_lint` tools and the turn's-end lint.
    - `built/`: what the flake builds of the CLI, `kanban.js`, at `$KANBAN_JS`, run on every golden case; `checks.cli-js` runs it, `npm run test:built`.
    - `fixtures/`: the transcript records, neutral turns, Submit's random events, random replies and a reply's sections as text, which the tests build on; `records.ts` also writes neutral turns as the Claude Code records the adapter reads back, and `cli.ts` runs a golden case through the CLI, by stdin and by a transcript, however the CLI is run; in `refresh.ts`, the transcripts, `gh` answers and random events the refresh is driven with; in `settings.ts`, the shipped defaults merged, and the settings files a read may find; and, in `raised.ts`, raised items made open, and the refs of those settled, as the tests ask after them.
    - `types/`: the declarations Node's type-check needs in place of the engine's, and the check that the bundled YAML parser's types match its package's.
- `nix/`: the flake's helpers.
  - `skills-devshell/`: the sub-flake that installs this repository's skills into `.agents/skills/`: skillspkgs' `claude-code-tools` combination, plus `coding-agent-kanban-turn-responses`, the retired skill that stays installed until its retirement removes it, and `design-hygiene-find-implicit-models`.
  - `scripts/`: the dev shell's startup scripts, the vendor bundles' build, check and lay steps, in `vendor/`, the CLI's builds, in `cli/`: `bundle.sh`, `kanban.js`; and the derived skill's build, check and lay steps, in `skill/`, with `wrap.sh`, which adds the Nix install's `scripts/kanban`, a wrapper running `kanban.js` with nodejs-slim's `node`.

## Build and test

Enter the dev shell with `nix develop` (or direnv); it links `plugin/node_modules` to the flake's build of the npm dependencies, lays the bundled libraries in `plugin/vendor/`, and installs the project's skills into `.agents/skills/`. Then:

- `tests`: the core's tests (`npm test` in `plugin/`).
- `typecheck`: type-check the core and its tests (`npm run typecheck`).
- `typecheck-plugin`: type-check the hooks against the engine's API, which Claude Code lays in `plugin/.claude-plugin/types/` when it loads the plugin.
- `plugin-test`: `claude plugin validate` and the engine-driven tests; needs the `claude` CLI.
- `plugin-build`: build the plugin as Claude Code loads it (`packages.plugin`: the manifest, `defaults/`, `hooks/`, `src/`, `types/`, `vendor/` with its bundled libraries, and `skills/` with the derived skill's build, its `scripts/kanban` wrapper included) and link it to `result-plugin`.
- `check-reproducible`: build each of the repository's own derivations in the plugin's closure (`kanban.js`, the skill's files, the vendor bundles, the skill with its wrapper and the plugin), then rebuild each with `nix build --rebuild`, which fails where a rebuild differs from the first build. The nixpkgs derivations it builds on aren't rebuilt.
- `refresh-skill`: lay the flake's `skills-folder`, the derived skill as a git install loads it, in `plugin/skills/` (`nix/scripts/skill/lay.sh`), naming any file there the flake no longer makes, to delete by hand; commit what it changes. Run it after a change to the fragments, the spec, the golden cases, the CLI or the core it bundles, or whenever `check` says the skill differs.
- `nix build .#skill-standalone`: the derived skill alone, the folder `packages.plugin` copies into `skills/`, for a harness that loads skills but not Claude Code plugins; never installed beside the plugin.
- `refresh-vendor`: lay the flake's bundled libraries in `plugin/vendor/` (`nix/scripts/vendor/lay.sh`), as the dev shell does on entry, naming any bundle there the flake no longer makes, to delete by hand; commit what it changes. Run it after `update-flake`, or whenever `check` says the bundles differ.
- `spec-build`: compile `plugin/spec/kanban.yaml` into `plugin/src/protocol/spec.ts` and `plugin/spec/kanban.json`, and `plugin/spec/fragments/` into `plugin/src/protocol/fragments.ts`, refusing a spec that doesn't parse strictly, fit its schema or hold together, and a fragment with a placeholder the spec has no value for; commit them all.
- `nix build .#kanban-js`: the CLI as `bin/kanban.js`, which runs under Node 20 or later with no `node_modules` and names no store path, with the YAML parser's licence in `share/licenses/yaml/`. Unbuilt, `node plugin/cli/kanban.ts` runs it.
- `check`: `nix flake check`: formatting (treefmt), `typecheck`, `tests`, the committed bundles against the flake's, the generated spec files against what the spec compiles to, the plugin's build with its skill under `skills/` and its wrapper running, `claude plugin validate` on it by nixpkgs' `claude-code`, the committed skill against the flake's, and `kanban.js` built and run on every golden case. A build has no engine, so `typecheck-plugin` and `plugin-test` run only in the dev shell; run them before a pull request that touches `plugin/hooks/` or `plugin/test/engine/`.

`menu` lists the dev shell's other commands.

To run a change in Claude Code:

- Every session runs the Nix-pinned install, `coding-agent-kanban-turns@nix-pinned`.
- This repository's dev session overrides it with the local build: `claude --plugin-dir result-plugin --continue`.
- After a change, run `plugin-build`, then `/reload-plugins` in that session. A new file reaches the build only once `git add` has staged it.

## Style

The plugin is pure functional TypeScript: small pure functions over readonly data, no mutation or classes, array pipelines over loops, one expression or one return per function where it reads, effects only in `plugin/hooks/` and the CLI's edge, `plugin/cli/kanban.ts`, and well-known libraries over hand-rolled code where the plugin's runtime can load them. Every pure function has a test in `plugin/test/unit/`. Settings go in `plugin/defaults/config.yaml`, never as values in code, as `config-hygiene-shipped-defaults` says, and the protocol's rules, which no user changes, go in `plugin/spec/kanban.yaml`: a list's glyph or header, a command's name or a rule character is read from `src/protocol/spec.ts`, never written into a pattern or a parser in the core. Prose that names a list, a kind or a command in words takes the name from the spec too: the agent's instructions are fragments in `plugin/spec/fragments/` whose placeholders the spec fills, and a short text such as the tool's description or a pane message reads the name from `src/protocol/rules.ts` or `spec.ts`. A new fragment goes in an output's list of fragments, `INSTRUCTION_FRAGMENTS` in `instructions.ts` or `SKILL_FRAGMENTS` in `tools/skill/render.ts`, or a test fails. Data and settings files are YAML, read strictly under the YAML 1.2 core schema with duplicate keys refused, by the `yaml` library in `plugin/vendor/`, never by a hand-written parser or a regular expression.

The pane, the reply's drawing and the draft's answers take one path for every list, with no per-list branch in code: they read a list's `feedback` and settling words from the spec and its labels from the settings, through a table keyed by the feedback, such as `READERS` in `src/items/answers.ts` or `ANSWER_VIEWS` in `hooks/register.tsx`, and compare no list's name to choose what to do. Raising and settling stay per list, by the spec: Todo items are read from a reply's own list and Decide items raised by `kanban_options`, and each list is settled as its `settled-by` says.

## The protocol's source

The plugin is the only source of the kanban protocol. The spec, fragments and golden cases in `plugin/spec/` hold it, and the plugin builds its skill from them. No rule is kept in step with another repository.
